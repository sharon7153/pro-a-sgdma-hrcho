1 개요

1.1 Sanity의 역할

Sanity는 RTL을 고칠 때마다 실행하는 회귀 게이트입니다. 목적은 레지스터 경로와 SG 기본 전송이 깨졌는지를 수 초 안에 판정하는 것이며, 기능을 넓게 검증하는 것이 아닙니다. 기능 검증은 SOR의 테스트 15개(T-01 ~ T-15)가 맡습니다. Sanity가 통과해도 SOR 테스트는 따로 실행하고, Sanity가 실패하면 SOR 테스트보다 먼저 원인을 해결합니다.

조건구현이유
짧은 실행 시간시뮬레이션 6,305 ns, 실행 수 초매 수정마다 실행하기 위함
자동 판정체크마다 [ ok ] / [FAIL], 요약에서 집계로그를 사람이 해석하지 않아도 됨
종료 코드실패 시 $fatal(1)스크립트·CI가 종료 코드로 판정
watchdog전역 #2_000_000 후 $fatal(1)handshake가 멈춰도 회귀가 끝나도록
// global watchdog - a hung handshake must not hang the regression    (tb_sg_dma.sv:716~721)
initial begin
  #2_000_000;
  $display("\n[FAIL] GLOBAL TIMEOUT - simulation did not finish");
  $fatal(1, "global watchdog");
end

전송 하나를 기다릴 때는 wait_irq에 별도 타임아웃(기본 50,000 클럭, tb_sg_dma.sv:366)이 있습니다. 이 타임아웃은 해당 TC의 FAIL 체크로 기록되어 어느 TC에서 멈췄는지 로그에 남습니다.

2.3 판정 규칙

상황동작
체크 통과[ ok ] 출력, TC pass +1
체크 실패[FAIL] + 기대값·측정값 출력, TC fail +1
TC 안에서 fail ≥ 1그 TC는 FAIL. 이후 TC는 계속 실행
VERSION 또는 IDENTIFICATION 불일치나머지 6개 TC를 SKIP하고 종료
FAIL 또는 SKIP이 1건 이상*** SANITY FAILED *** + $fatal(1)
모두 통과*** SANITY PASSED *** + $finish

중단 조건을 VERSION / IDENTIFICATION 둘로 한정한 이유. 초기 구현은 SAN-001의 체크가 하나라도 틀리면 나머지를 모두 SKIP했고, INTERFACE_DESCRIPTION_2 기대값이 틀렸을 때 정상 RTL인데도 TC 6개가 SKIP되었습니다(부록 C.3). INTERFACE_DESCRIPTION_1/2와 PERIPHERAL_ID는 구성 상수이므로, 값이 틀리면 버스 고장보다 기대값 오류일 가능성이 큽니다. 그래서 bus_ok 플래그(tb_sg_dma.sv:197)를 따로 두고 두 레지스터만 게이트로 씁니다. 구성 레지스터가 틀리면 다음 안내를 출력합니다.

note : build-configuration register mismatch - confirm the
       expected value before treating it as an RTL defect.

체크별 예외는 없습니다. 3.8의 구현 특성 체크 2개도 다른 체크와 똑같이 집계되므로, 틀리면 *** SANITY FAILED ***가 됩니다. 문서가 정하는 것은 실패의 해석입니다.

마스크를 풀면 쌓여 있던 이벤트가 바로 인터럽트로 나갑니다. 마스크를 풀기 전에 IRQ_PENDING에 0x3을 써서 비웁니다. IRQ_PENDING에 쓰면 실제로 지워지는 것은 IRQ_SOURCE입니다 (SFR §4.2.2).

SOR 연결: T-09 (IRQ-002~005) — Sanity는 마스크 0x1만 보며, T-09는 0x3, 0x2, 0x1, 0x0과 "비우지 않고 마스크 해제"를 봅니다. T-08 (IRQ-001, REG-016, DESC-006) — 체크 2는 EOT 인터럽트의 가장 단순한 경우이고, 체크 7은 T-08의 관측과 겹치며 SOR에서도 참고 체크입니다.

구현 특성인 이유

전송이 끝난 뒤 DESCRIPTOR_ID가 마지막 descriptor의 id를 계속 보여 주는 것은 util_axis_fifo의 구현 특성이며 ADI가 문서로 보장한 동작이 아닙니다. dmac_sg는 descriptor가 완료될 때마다 ID FIFO에서 하나를 꺼내고(dmac_sg.v:278~289), FIFO가 비면 출력이 갱신되지 않아 마지막 값이 남습니다. 선행 문서에는 "이전 전송의 stale 값이 보일 수 있다"는 경고가 있었으나, SAN-005가 앞선 SAN-004의 0xA0이 아니라 자기 체인의 0xB2를 읽어 이를 반증했습니다.

정리 후 확인된 추가 동작(SFR §4.6.2, P): HWDESC = 1이고 완료된 descriptor가 없으면 값이 정의되지 않고(시뮬레이션 X), HWDESC = 0이면 0입니다. Sanity는 두 경우 모두 읽지 않습니다.

해석 규칙 (SOR v2.0.0 §2.1과 같음)

SOR은 판정을 판정 / 참고 체크 / 관찰 기록 / 관측 후 확정으로 나누고, "DESCRIPTOR_ID의 전송 완료 후 값은 항상 참고 체크"로 정했습니다. 이 두 체크는 그 규칙의 대상입니다.

이 체크가 FAIL하면 RTL 결함보다 "구현이 바뀌었다"는 신호로 먼저 봅니다.

  1. dmac_sg.v와 util_axis_fifo.v가 바뀌었는지 확인합니다.
  2. 바뀌었고 나머지 44개 체크가 통과했다면 구현 특성의 변화입니다. 기대값과 이 문서를 고칩니다.
  3. 바뀐 것이 없는데 FAIL하면 RTL 문제로 조사합니다.

드라이버는 이 값을 완료 판정에 쓰지 않습니다. 완료는 EOT 인터럽트나 TRANSFER_DONE으로 확인합니다 (SFR §4.6.2).

현재 TB 처리: 2.3의 판정 규칙에 체크별 예외가 없으므로 이 두 체크도 게이트 판정에 들어갑니다. 향후 TB에서 두 체크를 경고(WARN)로 낮춰 게이트에서 빼는 것을 권장합니다. 바꿀 경우 체크 수 집계와 요약 형식이 달라질 수 있으므로 7.2 규칙대로 TB 헤더·이 문서·부록 B를 함께 고칩니다.
