1 SG DMA 개요

1.1 동작 개요

일반 DMA는 CPU가 레지스터에 소스·목적지·길이를 쓰고 시작하면 한 구간을 옮긴 뒤 인터럽트로 완료를 알립니다. 여러 구간을 옮기려면 CPU가 구간마다 다시 설정해야 합니다.

SG(Scatter-Gather) DMA는 전송 파라미터를 메모리의 descriptor에 둡니다. descriptor 하나는 한 구간의 소스·목적지·길이와 다음 descriptor 주소를 담고, descriptor들은 next_sg_addr로 이어져 chain을 이룹니다. CPU는 첫 descriptor 주소만 레지스터에 쓰고 시작하며, DMA는 LAST 플래그가 있는 descriptor까지 차례로 읽어 처리합니다. 완료 인터럽트는 EOT_IRQ 플래그가 켜진 descriptor에서만 납니다.

  • gather: 흩어진 여러 소스 구간을 연속된 목적지에 이어 씀
  • scatter: 연속된 소스를 여러 목적지 구간에 나눠 씀

1.2 표준 순서

아래 순서를 "표준 순서"라 부르며 각 테스트에서 씁니다 (SFR §7.2).

  1. 메모리에 descriptor 체인을 쓴다. 마지막 descriptor만 flags = 0x3 (LAST + EOT_IRQ).
  2. IRQ_MASK(0x080) ← 0x1 — SOT 마스크, EOT 허용.
  3. CONTROL(0x400) ← 0x5 — ENABLE + HWDESC.
  4. SG_ADDRESS(0x47C) ← 첫 descriptor 주소.
  5. TRANSFER_SUBMIT(0x408) ← 0x1.
  6. 완료 대기 (irq 또는 TRANSFER_DONE polling).
  7. IRQ_PENDING(0x084)을 읽고 같은 값을 다시 써서 지운다 (W1C).

3번과 5번의 순서를 바꾸면 전송이 시작되지 않고 에러도 없습니다. ENABLE = 0에서의 TRANSFER_SUBMIT 쓰기는 무시됩니다 (SFR §4.4.2).

1.4 Descriptor 형식 (48바이트)

Offset내용
+0x00flags — [0] LAST, [1] EOT_IRQ
+0x04id — DESCRIPTOR_ID(0x454)로 보임
+0x08목적지 주소 (하위 3비트 무시)
+0x10소스 주소 (하위 3비트 무시)
+0x18next_sg_addr (LAST = 0일 때 사용)
+0x24x_len = 바이트 수 − 1 (하위 24비트)
+0x20, +0x28, +0x2C2D 필드. 이 구성에서는 무시. 0으로 채움

x_len은 "바이트 수 − 1"입니다. x_len = 0은 1바이트, 0xFFFFFF는 16 MiB이며, 길이 0 descriptor는 만들 수 없습니다. DMA는 descriptor 하나를 48바이트 burst 한 번(8바이트 × 6 beat)으로 읽습니다.

1.5 이 구성의 특징과 범위

  • 소스와 목적지가 모두 AXI-MM이라 길이를 1바이트 단위로 지정할 수 있습니다. ADI 공식 testbench는 이 조합을 검증하지 않으므로 T-07이 중요합니다.
  • RTL은 SG, MM→MM, 단일 클럭 구성만 남기고 정리되었습니다(2026-10-17). 2D, cyclic, framelock, AXI-Stream 소스 등은 코드에 없습니다.
  • 검증 범위는 DATA_WIDTH = 64, ADDR_WIDTH = 32입니다. DATA_WIDTH = 32에서는 AWLEN과 WLAST 위치가 맞지 않는 AXI 위반이 관측되었습니다(정리 전 ADI RTL도 같음, SFR §11 #3).
  • 세 AXI master 포트 모두 RRESP/BRESP 에러를 검출하지 않습니다(SFR §4.6.3). T-15가 이 동작을 관측합니다.

2.3 "hang 없음"의 정의

자기 참조 체인이나 16 MiB 전송은 원래 시간 안에 끝나지 않습니다. 이 문서에서 "hang 없음"은 다음을 뜻합니다 (SFR §5와 같음).

  1. 시간 안에 스스로 끝나면 hang이 아닙니다.
  2. 끝나지 않더라도 CONTROL ← 0x4(ENABLE만 0) 후 (가) 세 AXI master가 50,000 클럭 안에 idle이 되고, (나) CONTROL ← 0x5로 다시 켜서 보낸 T-03 전송이 정상 완료되면 hang이 아닙니다.
  3. (가) 또는 (나)가 실패하면 hang입니다.

모든 테스트는 시작 전에 아래를 합니다. 단, T-01과 T-09 1단계(리셋 직후 읽기)는 HW 리셋 직후 아무 쓰기도 하기 전에 합니다. 여러 테스트를 한 시뮬레이션에서 이어 돌린다면 이 두 단계 앞에서 리셋을 다시 겁니다.

4 테스트 상세

T-01 레지스터 버스와 기본 구성 확인

  • 확인 내용: 레지스터 읽기·쓰기가 동작하는지, 구성 상수가 정한 파라미터와 맞는지.
  • 중요한 이유: 버스가 동작하지 않으면 다른 모든 결과를 믿을 수 없고, 구성이 다르면 다른 테스트의 기대값이 모두 달라집니다.
  • 절차
    1. 리셋 직후 0x000, 0x004, 0x00C, 0x010, 0x014를 읽는다.
    2. VERSION 또는 IDENTIFICATION이 틀리면 나머지 테스트를 모두 건너뛴다.
    3. SCRATCH(0x008)에 0xA5A5_5A5A를 쓰고 읽는다.
    4. 반전 패턴 0x5A5A_A5A5를 쓰고 읽는다 (stuck-at 비트 검출).
    5. 0x0000_0000을 쓰고 읽어 원복한다.

T-02 미구현 비트와 레지스터 접근 규칙

  • 확인 내용: RTL에서 제거된 기능의 비트·레지스터가 바뀌지 않는지, RO 레지스터·미정의 주소·부분 바이트 쓰기의 동작.

    1. 아래 표의 레지스터에 0xFFFF_FFFF를 쓰고 읽는다. CONTROL에 쓰면 ENABLE·PAUSE·HWDESC가 모두 1이 되므로 원복 전에는 TRANSFER_SUBMIT을 쓰지 않는다.

    3. VERSION(0x000)과 IRQ_SOURCE(0x088)에 0xFFFF_FFFF를 쓰고 읽는다. 쓰기 응답도 기록한다.
    4. SCRATCH에 0xFFFF_FFFF를 쓴 뒤 WSTRB = 4'b0001로 0x0000_00FF를 쓰고 읽는다.
    5. 원복: CONTROL ← 0x0, FLAGS ← 0x2, 0x410/0x414/0x47C ← 0x0, SCRATCH ← 0x0.

T-03 descriptor 1개 복사

T-06 체인 길이 1 ~ 32

  • 확인 내용: 체인 길이 N = 1부터 32까지 끝까지 처리하는지.
  • 중요한 이유: 체인 길이에 따라 SG 엔진 내부 FIFO(주소 1단, descriptor 1단, ID 4 entry)가 차고 비는 양상이 달라집니다. 특정 길이에서 체인이 끊기거나 멈추면 드라이버에서 바로 문제가 됩니다. Sanity는 N = 3만 봅니다.

    1. N = 1, 2, 4, 8, 16, 32로 반복한다. 구간 하나는 64바이트.

    4. 표준 순서로 시작하고 descriptor 읽기 횟수를 세며 [B2] 모든 구간과 guard를 검사한다.
    5. 시간이 허락하면 N = 128을 LONG 영역에 두고 한 번 더 한다.

T-08 중간 EOT와 DESCRIPTOR_ID

  • 확인 내용: 중간 descriptor에 EOT_IRQ를 켜면 그 descriptor가 끝날 때도 인터럽트가 나는지, DESCRIPTOR_ID(0x454)가 처리 중인 descriptor의 id를 순서대로 보여 주는지.
  • 중요한 이유: T-04가 "체인당 1회"를 본다면 이 테스트는 "원하면 중간에도"를 봅니다. DESCRIPTOR_ID는 디버깅에서 진행 위치를 확인하는 레지스터입니다.
  • 절차
    1. (중간 EOT) 128바이트 descriptor 4개, id = 0xC0 ~ 0xC3, flags = 0b10, 0b00, 0b10, 0b11로 체인을 만들고 표준 순서로 시작한다.
    2. irq가 올라올 때마다: IRQ_PENDING 읽기 → 같은 값 쓰기 → DESCRIPTOR_ID 기록 → 횟수 +1. irq가 내려갔다 다시 올라오는지 본다.
    3. (id 추적) 512바이트 descriptor 8개, id = 0xD0 ~ 0xD7, 마지막만 flags = 0b11로 체인을 만들고 시작한다.
    4. 전송 중 100클럭마다 DESCRIPTOR_ID를 읽어 기록한다 [B6].
    5. 완료 후 CONTROL ← 0x0, 이어서 CONTROL ← 0x1(HWDESC = 0)을 쓰고 DESCRIPTOR_ID를 읽는다.

T-09 IRQ_MASK와 W1C

  • 확인 내용: 마스크 설정 4가지에서의 인터럽트 발생과 IRQ_PENDING/IRQ_SOURCE 값, IRQ_PENDING에 1을 쓰면 IRQ_SOURCE가 지워지는지.
  • 중요한 이유: 드라이버 오류가 많은 부분입니다. 리셋 직후 모두 마스크(0x3)이고, 마스크된 동안에도 IRQ_SOURCE에 기록되어 마스크 해제 시 바로 인터럽트가 나며, 쓰는 주소(IRQ_PENDING)와 지워지는 레지스터(IRQ_SOURCE)가 다릅니다.
  • 절차
    1. HW 리셋 직후 다른 쓰기 전에 IRQ_MASK를 읽는다.
    2. 아래 4가지 설정마다: §2.4 공통 준비 → IRQ_MASK 설정 → T-03과 같은 전송. 표준 순서 2번과 7번은 건너뛴다. 시작 전에 TRANSFER_ID를 읽어 두고, 완료는 그 ID의 TRANSFER_DONE 비트를 polling해 기다린다. irq, IRQ_PENDING, IRQ_SOURCE를 기록한다.
    3. 0x1 설정에서: 읽은 IRQ_PENDING(0x2)을 그대로 쓰고 → IRQ_PENDING, IRQ_SOURCE, irq를 다시 본다.

    5. 같은 상황을 다시 만들고 이번에는 IRQ_PENDING ← 0x3 후 마스크를 푼다 → irq를 본다.

T-10 TRANSFER_SUBMIT 규칙과 연속 예약

  • 확인 내용: TRANSFER_SUBMIT의 세 규칙(ENABLE = 0에서 무시, 수락되면 자동 0, 1인 동안 다시 써도 요청이 늘지 않음)과, 체인 A 진행 중 체인 B를 예약할 수 있는지.
  • 중요한 이유: ENABLE 전의 제출은 에러 없이 무시되어 디버깅이 어렵습니다. 연속 예약이 안 되면 처리량이 떨어지고, 요청이 사라지면 데이터 일부가 옮겨지지 않습니다.
  • 절차
    1. (무시 확인) CONTROL = 0x0에서 TRANSFER_SUBMIT ← 0x1 → 다시 읽고 버스 활동이 없는지 본다 [B2]. 이어서 체인 두 개를 쓴다.
      • 체인 A: descriptor 0x0000_1300부터 3개, 소스 0x0001_A000부터 총 1,536바이트, 목적지 0x0002_8000
      • 체인 B: descriptor 0x0000_1400부터 3개, 소스 0x0001_C000부터 총 1,536바이트, 목적지 0x0002_A000
      • 각 체인은 마지막 descriptor만 flags = 0b11
    2. IRQ_MASK ← 0x1, CONTROL ← 0x5. TRANSFER_ID를 읽어 ID_A로 기록. SG_ADDRESS ← A, TRANSFER_SUBMIT ← 0x1 → 0이 될 때까지 polling.
    3. A가 수락된 직후 SG_ADDRESS ← B, TRANSFER_SUBMIT ← 0x1을 쓰고 곧바로 다시 읽는다 (B의 ID는 ID_A + 1).
      • 1이면: 0x1을 한 번 더 쓴다 (중복 요청 시험).
      • 0이면: B가 이미 수락된 것이므로 이 회차의 중복 요청 판정은 무효. A를 8개 이상으로 늘려 다시 한다. 정한 횟수만큼 해도 안 되면 "판정 불가"로 보고.
    4. B 제출 후 ACTIVE_TRANSFER_ID를 읽어 A가 아직 진행 중임을 기록한다.
    5. TRANSFER_DONE의 ID_A, ID_B 비트가 모두 1이 될 때까지 polling한다. 인터럽트가 오면 그때마다 지운다 (지우기 전에 C4 확인). 이후 TRANSFER_DONE, TRANSFER_ID, ACTIVE_TRANSFER_ID와 두 목적지 데이터를 확인한다.
    6. (ID 재사용) 체인 A를 하나씩 3번 더 보낸다. 각 전송은 해당 ID의 TRANSFER_DONE 비트가 1이 될 때까지 기다리고 인터럽트를 지운 뒤 다음을 보낸다. ID는 ID_A + 2, ID_A + 3, 다시 ID_A. 세 번째 제출 직전과 직후에 TRANSFER_DONE[ID_A]를 읽는다.
  • 통과 기준 (예외: 1단계는 전송이 없는 것이 정상이므로 C1~C4 미적용)

T-12 PAUSE와 재개

  • 확인 내용: 전송 중 PAUSE를 켜면 멈추고 끄면 멈춘 위치부터 이어 가는지, 데이터가 빠지거나 중복되지 않는지, TRANSFER_PROGRESS가 진행을 따라가는지. 체인에서의 PAUSE 제약을 기록합니다.
  • 중요한 이유: PAUSE는 ENABLE = 0과 달리 상태를 지우지 않아야 합니다. 재개 후 한 구간이라도 빠지거나 겹치면 데이터가 손상됩니다.

    1. 4 KiB descriptor 1개(x_len = 4095, 소스 0x0001_0000, 목적지 0x0002_0000)로 시작한다.
    2. 전송 중 100클럭마다 TRANSFER_PROGRESS(0x448)를 읽는다 [B6].
    3. 첫 목적지 B 응답 후 CONTROL ← 0x7을 쓴다.

T-15 에러 응답과 잘못된 descriptor

  • 확인 내용: AXI 에러 응답이나 극단적인 descriptor에서의 동작. 최소한 hang이 없는지.
  • 중요한 이유: ADI testbench와 현재 TB 모두 이 영역을 다루지 않았습니다. RTL은 에러 응답을 검출하지 않으므로, 잘못된 descriptor를 읽으면 에러 표시 없이 엉뚱한 주소로 전송해 시스템 메모리를 손상시킬 수 있습니다.

RTL 근거 (정리 후). m_src_axi_rresp, m_dest_axi_bresp, m_sg_axi_rresp는 sg_dma_top 포트로만 존재하고 내부에 연결되지 않습니다(sg_dma_top.v:98, :122, :141). 정리 전 ADI RTL도 응답 값을 레지스터·인터럽트로 내보내지 않았습니다. 따라서 아래 "예상 동작"은 RTL 분석(R)이며, 이 테스트가 처음 측정합니다. 응답 처리 경로를 확인할 때는 response_handler.v, axi_dmac_response_manager.v, src_axi_mm.v, dest_axi_mm.v를 먼저 읽습니다.

  • 절차: 각 경우마다 정한 시간을 기다린 뒤 §2.3 "hang 없음" 절차(ENABLE = 0 → idle 확인 → 재시작 → T-03 전송)를 한다.
    1. (소스 읽기 에러) 소스를 ERR 영역에 두고 읽기 응답을 SLVERR로 바꾼다 [B3]. DECERR로 한 번 더. 목적지를 ERR 영역에 두고 쓰기 응답을 SLVERR로 바꾸는 경우도 한다.
    2. (descriptor 읽기 에러) 3개 체인 중 두 번째 descriptor만 ERR 영역에 두고 읽기 응답을 SLVERR로 바꾼다 [B3]. 이때 읽기 데이터는 모두 0이다.
    3. (최대 길이) x_len = 0xFFFFFF(16 MiB) descriptor로 시작한다. 목적지는 다른 영역과 겹치지 않게 TB에서 정한다. 첫 목적지 쓰기를 확인한 뒤 끈다. 끝까지 보내는 시험은 시뮬레이션 시간 문제로 별도 검토.
    4. (자기 참조 체인) flags = 0b00이고 next_sg_addr가 자기 주소인 descriptor로 시작한다.
    5. 각 경우 irq, IRQ_SOURCE, TRANSFER_DONE, 버스 활동, 목적지 메모리, 주소 0x0000_0000 부근의 쓰기를 기록한다.
  • 통과 기준 (예외: C1~C4 미적용. 이 테스트 동안 B1 검사기는 기록만($error 대신 $info), C5는 관찰 기록, C6은 B1 외의 $error에만 적용)
